## 1. frontmatter 全字段定义表

字段格式：`---` 围栏内 YAML（gray-matter 解析，plan 已定案）。每个字段在下表给出：字段 / 类型 / 必填性 / 枚举与取值 / 默认值 / 校验规则 / 示例。

### 1.1 `project.md`（`PM/projects/<slug>/project.md`）

| 字段 | 类型 | 必填 | 枚举 / 取值 | 默认值 | 校验规则 | 示例 |
|---|---|---|---|---|---|---|
| `type` | literal | 是 | `"project"` | — | `z.literal("project")` | `project` |
| `id` | string | 是 | slug 规范化结果 | — | 与目录名一致，符合 §1.5 slug 规则；跨文件一致性由 parser/indexer 校验 | `my-app` |
| `name` | string | 是 | — | — | trim 后非空，长度 ≤ 100 | `我的应用` |
| `status` | enum | 是 | `active \| paused \| done \| archived` | — | 状态机合法性：见 §3.1（project 流转表） | `active` |
| `period` | `[date, date]` | 是 | ISO date ×2 | — | 元组：`start ≤ end`；两个元素各非空；格式 `YYYY-MM-DD` | `["2026-01-01", "2026-12-31"]` |
| `tags` | string[] | 是 | — | `[]` | 每元素 trim 后非空；整体去重（保序） | `["frontend"]` |

> **理由**：`status`/`period`/`tags` 在 plan §4.2 给出；`active/paused/done/archived` 四态在 plan §4.3 状态机部分推断，并在 §3.1 赋予合法流转规则，供 `pm move` 的反馈与 Web 标色共用。

### 1.2 `requirement`（`PM/projects/<slug>/requirements/REQ-<slug>-NNN.md`）

| 字段 | 类型 | 必填 | 枚举 / 取值 | 默认值 | 校验规则 | 示例 |
|---|---|---|---|---|---|---|
| `type` | literal | 是 | `"requirement"` | — | `z.literal("requirement")` | `requirement` |
| `id` | string | 是 | — | — | 匹配 `^REQ-[A-Za-z0-9一-鿿]+-\d{3}$`；id 中 slug 与目录 slug 一致 | `REQ-proj-001` |
| `title` | string | 是 | — | — | trim 后非空，长度 ≤ 200 | 支持 OAuth 登录 |
| `status` | enum | 是（frontmatter 必填；创建端点/CLI/Web 默认 pool：`05-server §2.5`、`03-cli §3.2`、`06-web §3.4`） | `pool` | 状态机合法性：见 §3.2（requirement 流转表）；流转副作用见 §3.2 | `pool` |
| `priority` | enum | 是 | `P0 \| P1 \| P2 \| P3` | — | 枚举值含义在 §7.1 数据字典 | `P2` |
| `module` | string | 是 | — | `""` | 任意字符串，空串允许（未分类） | `auth` |
| `source` | string | 是 | — | — | 非空；描述需求来源（如 `inbox:xxx.md`、`human:xxx`） | `inbox:2026-11-10-idea.md` |

### 1.3 `task`（`PM/projects/<slug>/tasks/TASK-<slug>-NNN.md`）

| 字段 | 类型 | 必填 | 枚举 / 取值 | 默认值 | 校验规则 | 示例 |
|---|---|---|---|---|---|---|
| `type` | literal | 是 | `"task"` | — | `z.literal("task")` | `task` |
| `id` | string | 是 | — | — | 匹配 `^TASK-[A-Za-z0-9一-鿿]+-\d{3}$`；与目录/文件名一致 | `TASK-proj-002` |
| `title` | string | 是 | — | — | trim 后非空，长度 ≤ 200 | 实现 OAuth 适配 |
| `status` | enum | 是 | `todo \| doing \| done \| cancelled` | — | 状态机合法性：见 §3.2（task 流转表） | `todo` |
| `requirement` | string | 是 | — | — | 匹配 `^\[\[REQ-[A-Za-z0-9一-鿿]+-\d{3}\]\]$`（wiki-link 字符串）；目标 requirement 必须在同一项目存在（由 `pm check` 的 dangling/orphan 检查覆盖） | `[[REQ-proj-001]]` |
| `priority` | enum | 是 | `P0 \| P1 \| P2 \| P3` | — | 同 requirement | `P2` |
| `estimate` | number | 否 | 人日 | `null` | `> 0`（详设允许小数） | `2.5` |
| `due` | date | 是 | — | — | 有效 ISO 日期；非空（任务语义需要时间线；若产品侧要求可选可另外扩展） | `2026-11-20` |
| `completed` | date \| null | 是 | — | `null` | `null` 或有效 ISO 日期；仅 `done` 流转设置 | `2026-11-20` |
| `created` | date | 是 | — | — | 有效 ISO 日期 | `2026-11-10` |
| `updated` | date | 是 | — | — | 有效 ISO 日期；校验规则 `updated >= created` | `2026-11-10` |

> **理由**：字段名与类型严格对应 plan §4.2；两处做了最小扩展并留入 [§5](#5-zod-schema完整代码级定义) 与 `docs/design/open-questions.md` 上报：
> - `estimate: number` 注释“可选”（plan）→ 默认 `null`，`optional()` 处理；
> - `due: date` 未标“可选”（plan）→ 设计为必填，scaffold 给值 = 今天；
> - `requirement` 字符串以 wiki-link 形式存（plan：单写原则，任务侧唯一写关联，见 §7.2）。

### 1.4 `inbox` 条目（`PM/inbox/<file>.md`）

| 字段 | 类型 | 必填 | 枚举 / 取值 | 默认值 | 校验规则 | 示例 |
|---|---|---|---|---|---|---|
| `type` | literal | 是 | `"inbox"` | — | `z.literal("inbox")` | `inbox` |
| `id` | string | 是 | — | — | 匹配 `^INBOX-[A-Za-z0-9一-鿿]+-\d{3}$`（见 §1.5 编号分配） | `INBOX-inbox-001` |
| `slug` | string | 否 | slug 规则 | `"inbox"` | 归属项目 slug，未归属使用 `inbox`（与 `ZInboxEntry.slug` default 一致，符合 `Slug` 正则 `^[A-Za-z0-9一-鿿]+(-[A-Za-z0-9一-鿿]+)*$`，见 `01-数据规范 §5`） | `proj` |
| `created` | date | 是 | — | — | 有效 ISO 日期 | `2026-11-19` |
| `tags` | string[] | 否 | — | `[]` | trim 后非空、去重 | `["想法"]` |
| `source` | string | 否 | — | — | 如 `human` / 来源描述 | `人工收集` |
| `archived` | date \| null | 否 | — | `null` | 整理归档日期（归档规则见 §1.8） | `2026-11-20` |
| 正文 | Markdown | 是 | — | — | 收集箱原始碎片文本（无 frontmatter 的普通文件视为未识别） | `- 需要加 OAuth 登录` |

> **理由**：plan §4.1 只规定 `PM/inbox/` 为收集箱，不约束 frontmatter；详设在 §1.8。`archived` 字段用于"归档"放在 inbox 子目录外（见 §1.8.3），避免索引识别到它。

### 1.5 编号分配规则

- **格式**：`<前缀>-<项目slug>-<序号>`（plan §4.3），前缀枚举：

| 类型 | 前缀 | 文件位置 |
|---|---|---|
| project | （无，id = slug） | `PM/projects/<slug>/project.md` |
| requirement | `REQ` | `PM/projects/<slug>/requirements/REQ-<slug>-NNN.md` |
| task | `TASK` | `PM/projects/<slug>/tasks/TASK-<slug>-NNN.md` |
| inbox | `INBOX` | `PM/inbox/*.md`，id 中 slug 取 frontmatter `slug`，默认 `inbox` |

- **序号**：三位零填充（`001`…`999`），与项目无关；跨文件稳定——不删除文件（用 `cancelled`），保证编号单调递增。
- **分配算法**（core `allocateId`，详见 [02-core.md §2.7](02-core.md#27-allocateid)）：
  1. 扫描目标目录所有文件的 `id` 字段；
  2. 取同前缀 + 同 slug 的最大序号，+1；不存在 → `001`；
  3. 写入落盘时若 mtime 冲突（有他人新写）→ 重新扫描重试；
  4. 序号 > 999 表示池耗尽 → 返回 `E_SEQ_EXHAUSTED`（不静默改格式，避免破坏"三位序号"规范）。
- **并发分配**：同前缀同 slug 下多个 writer 并发可能同取号——由 writer 的 mtime 冲突检测（02-core）自动重试；单写原则（plan §4.3）保证落盘串行。
- **slug 规范化策略**（中文项目名转 slug，§1.5 适用范围 = 目录名与 id）：
  1. 输入：项目名（中文或 ASCII），trim；
  2. 转换为小写 ASCII（ASCII 字母转小写，其它非汉字 Unicode 保留原字符，文件名安全）；
  3. 空格 → `-`，连续 `-` 合并为一个，去首尾 `-`；
  4. 移除 `/ \ : * ? " < > |` 及控制字符（文件名非法字符）；
  5. 与已存在 `PM/projects/` 重名 → 追加 `-2`、`-3`…直至唯一；
  6. 最终示例：`我的应用 v2` → `我的应用-v2`；`My App` → `my-app`。
  > **理由**：plan §4.1 "项目目录名即 slug"；汉字在 Windows/Obsidian 合法且可读，移除非法字符与小写化保证跨平台一致，冲突追加数字后缀保证唯一性；默认 slug `inbox`，与 `ZInboxEntry.slug`（`01-数据规范 §5`）default 一致，`INBOX-inbox-001` 形式与 `ZInboxEntry.id` 正则一致（R-101 后收敛）。

## 3. 状态机

> 与 plan §4.3 状态枚举一致；合法流转由本节定义，非法流转必须被拒绝并给出原因（plan）。

### 3.1 project 流转表

| 流转 | 合法性 | 触发方 | 流转副作用 |
|---|---|---|---|
| active → paused | 合法 | agent | `updated=<今天>` |
| paused → active | 合法 | agent | `updated=<今天>` |
| active → done | 合法 | agent | `updated=<今天>` |
| active → archived | 合法 | agent | `updated=<今天>` |
| done → archived | 合法 | agent | `updated=<今天>` |
| paused → done | 非法 | — | — （ paused 需先回 active） |
| done → active / done → paused | 非法 | — | — （done 为终态，不可回退） |
| archived → * | 非法 | — | — |

> **理由**：paused 走向 done 需先 active（保证"done"语义 = 确认完成后归档）；done 终态维持了数据可追溯性与 Web 看板中“已结束”的语义。

### 3.2 requirement 流转表

| 流转 | 合法性 | 触发方 | 流转副作用 |
|---|---|---|---|
| pool → reviewing | 合法 | agent（提交整理完成） | `updated=<今天>` |
| pool → rejected | 合法（直接拒绝） | agent | `updated=<今天>` |
| pool → done | 非法 | — | — |
| reviewing → accepted | 合法（接受） | agent 或人 | `updated=<今天>` |
| reviewing → rejected | 合法 | agent | `updated=<今天>` |
| reviewing → done | 非法 | — | — |
| accepted → done | 合法（接受后派发/完成） | agent | `updated=<今天>` |
| accepted → reviewing | 非法 | — | — |
| accepted → rejected | 非法 | — | — |
| rejected → pool | 合法（退回重塑） | agent/人 | `updated=<今天>` |
| rejected → reviewing / done | 非法 | — | — |
| done → * | 非法（done 终态） | — | — |

> **理由**：`accepted → done` 是唯一"派生任务/完成接受"节点；`rejected → pool` 允许修改后重新进入待处理。`done` 终态避免被重新激活改写，与 project 一致。

### 3.3 task 流转表

| 流转 | 合法性 | 触发方 | 流转副作用 |
|---|---|---|---|
| todo → doing | 合法（开始） | agent/人 | `updated=<今天>` |
| todo → done | 合法（补签完成） | agent/人 | `updated=<今天>`，`completed=<今天>` |
| todo → cancelled | 合法（取消） | agent/人 | `updated=<今天>` |
| doing → done | 合法（完成） | agent/人 | `updated=<今天>`，`completed=<今天>` |
| doing → cancelled | 合法（取消） | agent/人 | `updated=<今天>` |
| doing → todo | 非法（回退不允许） | — | — |
| done → * | 非法（done 终态） | — | — |
| cancelled → todo | 合法（重新开始） | agent/人 | `updated=<今天>` |
| cancelled → done / doing / cancelled | 非法 | — | — |

> **理由**：`done` 的两个入口（todo 直接、doing 经由完成）都设置 `completed`，保证字段语义统一；`doing → todo` 不允许回退（避免任务时间线被随意扭转）。

### 3.4 非法流转清单

所有未列在 3.1–3.3 表中的流转（含同状态）均为非法，`pm move` / `POST /api/.../patch` 返回 `E_INVALID_TRANSITION`（09-cli/03 定义退出码映射，见 [03-cli.md](03-cli.md#exit-codes)），响应中包含：

```ts
{
  file: "E:\\repos\\project-manage\\...\\TASK-proj-001.md",
  code: "E_INVALID_TRANSITION",
  message: "非法状态流转: todo -> done 已合法..." | 实际：以非法为例 "doing -> todo 不可逆回退，拒绝流转"
}
```

流转副作用定义（除 `updated` 外）：`completed` 仅在 3.3 第二行/第四行触发；`pm move` 默认操作者 = `Config.defaultAuthor`（非状态字段，可在 frontmatter 增加可选 `agent: string`？— 暂不加，详设 02-core 的 `write` 工具带 actor 参数）。

> **理由**：非法清单必须"必须被拒绝并给出原因"（plan）；每条错误响应结构统一（§4 中的 ErrorModel）。

## 4. 校验与降级策略

> plan §4.3 第 6 条：frontmatter 校验失败的文件进入"待修复"清单，UI 提示但不崩溃。详设：

- `validateAll(index)`（02-core）返回每个非法文件的详细 `issues`（Zod `ZodIssue` 列表，带 `path` 到具体字段），错误报告精确到 `file + field`（`pm validate` 约定，见 03-cli）。
- 分类：
  - `Zod` 解析失败（字段缺失/类型错/枚举越界/正则不匹配）→ `broken` 清单（`ValidateResult.code = E_VALIDATION`）。
  - 文件路径/id 不一致（id 与目录名）→ `broken`。
  - 日期倒挂（`updated < created` 或 `due < created`）→ `pm check` 报告（约定在 03-cli `check`）。
  - wiki-link 悬空（`E_DANGLING_WIKI`）/ 无效链接目标 → `pm check`。
- "待修复"清单在 Web 首页以黄色禁止图标 + 链接到详细 `pm validate` 输出展示（未崩溃、可用）。

## 5. Zod schema 的完整代码级定义

完整可导入代码（`@pm/core` 或 `packages/core/src/schema/`）：

```ts
// packages/core/src/schema/date.ts
import { z } from "zod";

/** ISO 日期 "YYYY-MM-DD" */
export const IsoDate = z
  .string()
  .regex(/^\d{4}-\d{2}-\d{2}$/, "需为 YYYY-MM-DD 形式的 ISO 日期")
  .refine((s) => {
    const [y, m, d] = s.split("-").map(Number);
    const dt = new Date(Date.UTC(y, m - 1, d));
    return (
      dt.getUTCFullYear() === y &&
      dt.getUTCMonth() === m - 1 &&
      dt.getUTCDate() === d
    );
  }, "不是合法日历日期（如 2026-02-30）");

// packages/core/src/schema/slug.ts
/** 项目 slug：ASCII 小写字母数字 + 汉字 + "-" 连接，不允许连续/边缘 "-" */
export const Slug = z
  .string()
  .regex(/^[A-Za-z0-9一-鿿]+(-[A-Za-z0-9一-鿿]+)*$/, "slug 非法（需为字母数字或中文，中间以单 "-" 连接）")
  .max(80);

// packages/core/src/schema/requirement.ts
export const ProjectStatus = z.enum(["active", "paused", "done", "archived"]);
export const ReqStatus = z.enum(["pool", "reviewing", "accepted", "rejected", "done"]);
export const TaskStatus = z.enum(["todo", "doing", "done", "cancelled"]);
export const Priority = z.enum(["P0", "P1", "P2", "P3"]);

export const ZProject = z.object({
  type: z.literal("project"),
  id: Slug,
  name: z.string().min(1).max(100).transform((s) => s.trim()).refine((s) => s.length > 0),
  status: ProjectStatus,
  period: z.tuple([IsoDate, IsoDate]).refine(([s, e]) => s <= e, "period[0] 必须 ≤ period[1]"),
  tags: z
    .array(z.string().min(1).transform((s) => s.trim()).refine((s) => s.length > 0))
    .refine((arr) => new Set(arr).size === arr.length, "tags 去重"),
});

export const ZRequirement = z.object({
  type: z.literal("requirement"),
  id: z.string().regex(/^REQ-[A-Za-z0-9一-鿿]+-\d{3}$/, "id 需形如 REQ-<slug>-NNN"),
  title: z.string().min(1).max(200),
  status: ReqStatus,
  priority: Priority,
  module: z.string().default(""),
  source: z.string().min(1),
  created: IsoDate,
  updated: IsoDate,
}).superRefine((v, ctx) => {
  if (v.updated < v.created) ctx.addIssue({ code: "custom", path: ["updated"], message: "updated 不能早于 created" });
});

export const ZTask = z.object({
  type: z.literal("task"),
  id: z.string().regex(/^TASK-[A-Za-z0-9一-鿿]+-\d{3}$/, "id 需形如 TASK-<slug>-NNN"),
  title: z.string().min(1).max(200),
  status: TaskStatus,
  requirement: z
    .string()
    .regex(/^\[\[REQ-[A-Za-z0-9一-鿿]+-\d{3}\]\]$/, "requirement 需形如 [[REQ-<slug>-NNN]]"),
  priority: Priority,
  estimate: z.number().optional().refine((n) => n === undefined || n > 0, "estimate 为正数（人日）"),
  due: IsoDate,
  completed: z.union([IsoDate, z.null()]),
  created: IsoDate,
  updated: IsoDate,
}).superRefine((v, ctx) => {
  if (v.updated < v.created) ctx.addIssue({ code: "custom", path: ["updated"], message: "updated 不能早于 created" });
});

export const ZInboxEntry = z.object({
  type: z.literal("inbox"),
  id: z.string().regex(/^INBOX-[A-Za-z0-9一-鿿]+-\d{3}$/, "id 需形如 INBOX-<slug>-NNN"),
  slug: Slug.default("inbox"),
  created: IsoDate,
  tags: z.array(z.string().min(1).transform((s) => s.trim()).refine((s) => s.length > 0)).default([]),
  source: z.string().optional(),
  archived: z.union([IsoDate, z.null()]).default(null),
});

// 类型导出（供 02-core 等处使用）
export type Project = z.infer<typeof ZProject>;
export type Requirement = z.infer<typeof ZRequirement>;
export type Task = z.infer<typeof ZTask>;
export type InboxEntry = z.infer<typeof ZInboxEntry>;
```

> **理由**：Zod 是 plan 定案校验库；`d.ts` 中每个字段的必填性/枚举/校验规则与 §1 表一致；`transform().refine()` 链用于统一 trim 与非空语义；`superRefine` 用于跨字段约束（`updated ≥ created`）。

## 6. wiki-link 关联与反链聚合规则

> plan §4.3 第 1 条：任务→需求的关联只写在任务侧（`requirement` 字段）；需求的关联任务列表由后端解析反链聚合，不落盘。

### 6.1 单写原则

1. 任务→需求：唯一写入点 = 任务 frontmatter `requirement` 字段（§1.3），wiki-link 格式 `[[REQ-<slug>-NNN]]`。
2. 需求→任务：不写相反字段，由 core 每次索引构建时聚合（02-core `deriveRequirementTasks`，详见 [02-core.md §3.2](02-core.md#32-deriveRequirementTasks)）。

### 6.2 链接格式与校验

- 写法：`[[REQ-<slug>-NNN]]`，与 plan §4.2 一致。
- 解析：`parseWikiLinks(body: string): string[]`（02-core，聚合阶段复用）。
- 校验（`validateAll`）：
  - 目标 id 必须在同项目 `requirements/` 中存在 → 否则 `E_DANGLING_WIKI`（仅 `pm check` 报告，frontmatter 本身 Zod 通过，以便聚合忽略悬空）。
  - 目标 id 的 slug 必须与任务文件所在项目一致（跨项目关联禁止）：跨项目 → `E_DANGLING_WIKI`（"目标不在当前项目"）。
  - 无效格式（如 `[[xxx]]` 不匹配 `^\[\[REQ-...\]\]$`）→ `E_VALIDATION`。

### 6.3 反链聚合（不落盘）

`deriveRequirementTasks(index): Map<string, string[]>`：

```ts
// key: REQ id; value: TASK id 数组，按 id 升序（字典序 = 编号递增序，NNN 三位保证）
```

- 只统计 `status ≠ cancelled` 的任务？— 不区分：完整聚合，由 UI 按状态过滤（原因：聚合只做聚合，过滤是展示逻辑，源数据不丢）。

## 7. inbox 模式规范

### 7.1 模式定位

plan §4.1：`PM/inbox/` = 收集箱，"人随手丢想法，代理整理成规范需求"。本节为该模式的文件格式、整理流程、归档规则。

### 7.2 文件格式

- 目录：`PM/inbox/`（根），`PM/inbox/archive/`（归档）；**索引/聚合只扫 inbox 根**，不扫 `archive/`（决定于 §7.5）。
- 文件：Markdown，`frontmatter` 见 §1.4，正文自由文本。
- 整理产物（由 agent/人）：生成 `PM/projects/<slug>/requirements/REQ-<slug>-NNN.md`，`title` 取从碎片提炼的核心语句，`module`/`source` 由 agent 猜测/回填（agent 需保持 `updated=created` 一致）。

### 7.3 整理流程（给 `pm inbox process` 的交互契约）

1. **收集**：人/agent 在 inbox 根直接创建或复制 md 文件（可不带 frontmatter——视为"未识别编号"）。
2. **扫描展示**：`pm inbox list [--json]` → 按 `created`/`id` 倒序列出 `{id, created, tags, source, body首行}`。
3. **整理**：代理按产物要求填写需求字段 → `pm new requirement --slug <slug> --title ... --module ... --source ...`。
4. **归档**：`pm inbox archive <id>` → 移动到 `PM/inbox/archive/<id>.md`（文件名保持原样），原文件 `frontmatter.archived = <今天>`（如有 frontmatter，补齐缺失字段：`type/id` 等）。

### 7.4 归档规则

- 归档动作：文件物理移动到 `PM/inbox/archive/`；`archived` 字段置归档日期。
- **不回溯影响**：归档只影响 inbox 索引视图，不影响已生成的 `requirement`。
- 未归档条目（`PM/inbox/*.md` 根级）持续被 `pm inbox list` 展示；`archive/` 子树排除。

### 7.5 索引与降级约定（自忽略）

- `buildIndex` 只扫 `PM/inbox/`（深度 1，不含 archive/），属于 `inboxEntries`；frontmatter 不合法 → `broken`（与 plan §4.3 待修复，UI 提示但不崩溃）。
- 无法识别类型的 md 文件（无 `type` 字段，或 type 未知）→ 计入 `unnumbered`（`UnnumberedFile[]`，02-core 详见），`pm validate` 报错 `E_VALIDATION`（精确到 file+field）。

### 7.6 inbox 编号

- `INBOX-<slug>-NNN`：slug 取 frontmatter `slug` 字段（默认 `inbox`），序号按 `allocateId("INBOX", slug)` 分配（与 requirements/tasks 独立前缀空间，理由：inbox 条目与 project 无强关联，统一前缀容易产生混淆）。
